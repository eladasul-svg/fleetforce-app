# Routing module — deviations from the work order

Companion to `routing-module.md`. Each entry: what was planned, what was done, why.
The design's shape is kept throughout: demand (`Route_Job__c` → `Job_Visit__c`) separate from the
plan (`Route_Plan__c` → `Route__c` → `Waypoint__c`), visits pointing to waypoints, an append-only
`Route_Event__c`, and the solver behind `RoutingProvider`.

## R0 Orient

**D-R0-1 · Branch not created.** Planned: create `feature/routing-module`. Done: the branch already
existed on origin (it carries the design doc commit `e2c8de4`), so it was checked out and tracked
instead. Why: the kickoff instruction said so.

**Orientation notes (inputs for later tasks, not deviations):**

- `AssistantToolsTest.definitionsDescribeSixTools` and `AssistantServiceTest` assert that exactly 6
  tools are sent to Claude. Routing tools therefore cannot be added to `AssistantTools.definitions()`;
  they are added only for sessions opened on a `Route__c` record (see R4).
- `Service_Ticket__c.In_Shop__c` is a formula checkbox (started and not ended), so "open in-shop
  ticket" is read directly from it.
- Fuel type `Electric` (global value set `Fuel_Type`) identifies EVs; `Fleet_Asset__c.Max_Range__c`
  and `Battery_Capacity_kWh__c` already exist.
- Permission sets: `FleetforceAdmin`/`FleetAdmin` are large admin sets, `FleetforceAssistantUser`
  grants only the assistant objects. Routing FLS goes in a new `FleetforceRouting` set (see R2).

## R1 Routing service

**D-R1-1 · Locked stops are played forward by the service, not pinned through VROOM.** Planned:
check whether VROOM's `vehicles[].steps` can pin stops. Done: it cannot as a hard constraint (it is an
initial-solution hint), so `options.fixed[] = {vehicle_id, task_ids[]}` is simulated in the service
from the vehicle's start and clock, and the solver starts from the last locked stop at its departure
time, exactly as the design's fallback describes. A locked stop that is already past its window is
kept and reported with `late_seconds`.

**D-R1-2 · Skill names are mapped to integers in the service, not in Apex.** Planned:
`RoutePlanService.buildRequest` maps skill names to integers. Done: the contract takes skill strings
and the service maps them. Why: one mapping in one place, readable requests in logs, and the Apex
stays provider-neutral (ORS/Google adapters would need their own mapping anyway).

**D-R1-3 · Unassigned reasons are diagnosed by the service.** VROOM reports which tasks it could not
place but not why. The service checks skills, then capacity, then reachability inside the time window
and shift, and otherwise reports `no_room`.

**D-R1-4 · OSRM image.** The design names `osrm/osrm-backend`; the maintained image is now published as
`ghcr.io/project-osrm/osrm-backend` (same project), pinned to `v5.27.1`. The VROOM docker image is not
needed because VROOM runs in-process through `pyvroom` 1.15.2, as designed.

**D-R1-5 · `balanced` objective.** VROOM has no workload-balancing objective, so `balanced` caps tasks
per vehicle at ⌈tasks / vehicles⌉ + 1 and adds a distance cost. `min_vehicles` adds a large fixed cost
per vehicle used.

**D-R1-6 · Docker not exercised here.** The cloud session has Docker on the path but no daemon access was
tried and there are no GCP credentials; the Dockerfiles, compose file, `cloudbuild.yaml` and
`service.yaml` are written but unbuilt. All 35 pytest tests run on `HaversineMatrix`, with OSRM
responses mocked through `httpx.MockTransport`.

## R2 Metadata

Generated by `scripts/routing/gen_routing_metadata.py` (kept so the field list can be regenerated in one
place; `python3 scripts/routing/gen_routing_metadata.py . --permset-only` rewrites just the permission
set once classes exist).

**D-R2-1 · A separate `FleetforceRouting` permission set.** Planned: "permission set field access".
Done: a new set with CRUD on the six routing objects, read on the fleet objects routing reads, create/
edit on `Allocation__c`, and FLS for every new field. The four new `Fleet_Asset__c` fields were also
added to `FleetAdmin` and `FleetforceAdmin` so existing admins see them. Why: routing is a module a
customer may not license, and keeping it out of the large admin sets keeps that separable. Master-detail
and required fields are left out of `fieldPermissions` because the platform refuses them there.

**D-R2-2 · `Route_Event__c` is create + read only in the permission set,** and the field permissions are
read-only. The append-only rule itself is enforced in Apex (`RouteEventTrigger`, R3) so it also binds
admins with Modify All.

**D-R2-3 · Added fields not in the design table** (shape unchanged):

- `Route_Job__c.Unassigned_Reason__c`: the reason the last optimization gave (skills, capacity, …), so a
  dispatcher sees why a job is unplanned without opening the solver JSON.
- `Waypoint__c.Late_Minutes__c` and `Solver_Step_Id__c`: lateness of a locked stop, and the id the
  solver used (visit Id or break id) so results map back to records.
- `Capacity_Dimension__mdt.Slot__c` and `Scale__c`: the slot number, and a multiplier that turns m³ into
  whole litres for the solver, which only plans in integers.
- `Route_Event__c.Type__c` gains `Optimized`, `Published` and `Optimization Failed` for the plan-level
  events the Queueable writes.
- `Route_Plan_Update__e` carries `Route_Plan_Id__c`, `Route_Id__c`, `Status__c`, `Revision__c`, `Message__c`.

**D-R2-4 · `Route_Plan__c.Error__c` is a long text area,** not a 255-character text area, so a full
callout error fits.

**D-R2-5 · Skills picklists.** `Route_Job__c.Required_Skills__c` (Refrigerated, Lift Gate, Wheelchair Ramp,
Tow Hitch, Hazmat, Forklift, Heavy Lift) is the union of vehicle features and driver skills;
`Fleet_Asset__c.Vehicle_Features__c` holds only the four vehicle features from the design. Driver skills
come from valid `Driver_Qualification__c` names (R3).

**D-R2-6 · Not validated against an org.** There is no `sf` CLI or org in the cloud session. Every file
is well-formed XML with elements in Metadata API order; the first scratch-org deploy is the real check.
Tabs were added to the FleetOps app (with console mappings) for Route Plans, Routes, Route Jobs and
Route Events; Job Visits and Waypoints are reached through related lists.

## R3 Apex integration

**D-R3-1 · DTOs are maps on the wire.** The contract's snake_case keys include words Apex reserves
(`type`, `end`), so `RoutingDtos` builds requests with `toMap()` and parses responses from untyped JSON
instead of `JSON.serialize` on typed classes. The classes still mirror `schemas.py` one to one.

**D-R3-2 · Task ids are record Ids.** A one-visit job is sent with the `Job_Visit__c` Id as its id; a
pickup→drop job is a shipment with the `Route_Job__c` Id and its two visit Ids as step ids. Results map
straight back to visits without a lookup table. Jobs with more than two visits, or two visits that are
not one Pickup plus one Delivery, are skipped with a reason (`Unassigned_Reason__c = skipped: …`).

**D-R3-3 · Soft windows.** The design says soft windows "become a cost in the solver". VROOM only has hard
windows, so a soft window (`Hard_Window__c = false`) is sent with 30 minutes of slack after its end
(`SOFT_WINDOW_GRACE_MINUTES`). Hard windows are sent as is.

**D-R3-4 · EV charging is a 30-minute break.** EVs (`Fuel_Type__c = Electric`) get one `charge` break
between 11:30 and 13:30 depot time, which becomes a `Charge` waypoint. There is no charger location data
yet, so the stop is wherever the van is; range-based charging needs charger sites (Place__c, deferred).

**D-R3-5 · Shifts.** Taken from `Schedule_Assignment__c` → `Schedule_Window__c` (Available/Required windows
for the plan's weekday, by asset first, then by driver), else 07:00–17:00 in the depot branch's time zone.

**D-R3-6 · Eligibility lives in `RoutingPolicy` from R3.** The "never allowed" rules (in-shop ticket,
expired licence or mandatory qualification) are needed to build a request, so `RoutingPolicy` was started
in R3 and R4 adds the approval rules to it. `In_Shop__c` is a formula on `TODAY()`, so it is read, not
filtered on, and `Status__c = In-Shop` also counts.

**D-R3-7 · Added classes:** `RoutingProviders` (factory, named-credential names, shared HTTP and error
text, `RoutingException`), `RouteEvents` (event builder and the append-only rule for
`RouteEventTrigger`), and `RoutingTestData` (test factory plus an HTTP mock that answers like the
service). `RoutePlanService.publishPlan` creates the `Allocation__c` per route after the motorpool's
overlap check.

**D-R3-8 · `openrouteservice` gets its own named and external credential** (`Openrouteservice`,
`Authorization` header), next to `FleetForce_Routing` (`X-FleetForce-Key` header). The FleetForce Routing
URL in the named credential is a placeholder (`https://fleetforce-routing.example.run.app`) until the
Cloud Run URL exists.

**D-R3-9 · Not compiled.** No org in the cloud session. Every class parses with the Apex parser that
`prettier-plugin-apex` uses (which catches syntax and reserved words, not types), and the tests were
written against the scenario data in `RoutingTestData`. The first scratch-org deploy and test run is
the real check; expect a few compile fixes.

## R4 Assistant tools and policy

**D-R4-1 · Routing tools are added only in chats opened from a `Route__c` record.** Planned: add the tools
to `AssistantTools` or a registered `RoutingAssistantTools`. Done: `RoutingAssistantTools`, which
`AssistantService` adds to the tool list (6 + 8) and the context prompt only when the session's
`Record_Id__c` is a Route. Why: the existing tests assert exactly 6 tools for other chats, and a
non-route chat has no use for them. The existing assistant tests are unchanged.

**D-R4-2 · No DML while tools run.** A turn may make a Claude callout and then a solver callout, and
Salesforce forbids a callout after uncommitted DML. So `report_delay` (the one tool that writes without a
proposal) and the "Handoff Proposed" event are buffered and written by `RoutingAssistantTools.commitPending`
together with the turn's own messages. Approving a proposal is DML only: the solver result is stored in
the proposal (`RoutingDtos.toContractJson`) and re-applied, and the approval is refused if the route's
remaining stops changed in between ("ask for a new re-plan").

**D-R4-3 · Who is the driver.** The running user is the route's driver when their User is the driver
Contact's `Related_User__c`; everyone else is treated as a dispatcher. `RoutingPolicy.approvalError`
blocks a driver from approving a change that needs a dispatcher. The guest driver app (no login) is not
wired to the assistant yet: that waits on the open question about Experience Cloud logins.

**D-R4-4 · Policy settings** live in `Routing_Policy_Setting__mdt` (record `Default`):
`Driver_Approves_Reorder__c`, `Driver_Approves_Breaks__c`, `Late_Tolerance_Minutes__c` (the last is
read by nothing yet; hard windows always need a dispatcher).

**D-R4-5 · `report_delay` "moves the route clock forward" through events.** It writes `Delay Reported`
only; the next `reoptimize_remaining` adds every delay reported since the last `Reoptimized` event to the
start time. ETAs on waypoints are not shifted until the re-plan is approved.

**D-R4-6 · `what_if` change types.** Implemented: take routes' vehicles out (`exclude_route_ids`) and
delay every start (`extra_delay_minutes`). It re-solves the plan's Ready/Planned jobs and compares KPIs;
nothing is saved.

**D-R4-7 · One invocable for all tools.** Salesforce allows one `@InvocableMethod` per class, so
`RoutingActions` exposes one "FleetForce Routing Tool" action with a tool name and JSON input (the same
schema the assistant sees). A change comes back as a proposal; a second call with `approveProposalJson`
applies it under the same policy.

**D-R4-8 · `ModelProvider`.** `AssistantClaudeClient` implements it and stays the default
(`ModelProviders.current()`); `AssistantService` now calls through the interface. `OpenAICompatibleProvider`
has the message and tool mapping implemented and tested, but its callout needs a customer-supplied named
credential, so it throws until one is set. `SalesforceModelsApiProvider` is a pure stub: the
`aiplatform` Models API classes only compile in orgs with Einstein generative AI, so it cannot reference
them from the core package. There is no setting yet to switch providers.

**D-R4-9 · LWC.** `fleetforceAssistant` shows a proposal's own `title` when it has one (routing
proposals), and treats any action other than `create` as an update (Current/Proposed columns).

## R6 UI

**D-R6-1 · `routePlanBoard` is built but not placed on a page.** The LWC (map with one colour per
route, a stop list per route, KPIs, Optimize / Re-optimize and Publish, the jobs that were not planned
and why) targets the `Route_Plan__c` record page. No flexipage was generated: Lightning record pages are
easiest to place in App Builder, and a generated one would overwrite the default page. It listens to
`Route_Plan_Update__e` through `lightning/empApi` and refreshes when the solver is done.
`RoutePlanController.getBoard` is cacheable and only reads; `optimize` and `publish` are not cacheable.

**D-R6-2 · The driver app's Route tab has no assistant panel yet.** Planned: a route tab "with the
assistant panel". Done: a `Route` tab (`driverRoute` LWC, `DriverRouteController`) with today's
remaining stops, ETAs, windows, access notes and a Navigate link to the next stop. The assistant needs a
named user with the assistant permission set, and the driver app runs on the guest site with a driver
picker, so the panel waits on the open question about Experience Cloud logins. `DriverRouteController`
follows `DriverAppController` (without sharing, driver as a parameter) and the guest profile needs class
access to it (see the local next steps).

**D-R6-3 · A pre-existing lint error in `driverApp.js`.** `dateText` was an arrow function that
prettier and ESLint's `no-confusing-arrow` format in opposite ways, so the pre-commit hook could not pass
on any change to the file. It is now a plain function with the same behaviour.

## Local session 1 (2026-11-03, compile and test)

First deploy of `force-app` to `fleetforce-dev-13` (namespaced scratch org, `--no-data`) and the first Apex
test run. The design's shape is unchanged; every fix is a compile, permission or test-idiom fix. Commits
`ac98ce9` and `d66f36b`.

**D-L1-1 · Reserved identifiers.** The Apex parser accepts `system` and `any` as names; the compiler does not.
`OpenAICompatibleProvider.toChatRequest` now uses `systemTexts`, `RoutePlanService.capacity` uses
`hasCapacity`. Every other class that failed on the first deploy failed only because it depends on these two.

**D-L1-2 · Child relationships need `__r`.** The subqueries used `FROM Visits`, `FROM Waypoints`,
`FROM Routes` and `FROM Job_Visits` (and `j.Visits` etc.). Custom child relationships are `Visits__r` and so
on. The relationship names in the generated field metadata were right, so only the Apex changed
(`RoutePlanService`, `RoutingAssistantTools`, `RoutePlanServiceTest`, `RoutingAssistantToolsTest`).

**D-L1-3 · `FleetforceRouting` reads the master objects too.** The platform refuses read on a detail object
without read on its master: `Driver_Qualification__c` needs `Contact`, `Schedule_Assignment__c` needs
`Fleet_Schedule__c`. `Schedule_Window__c` (the shift windows `RoutePlanService` reads) was missing as well.
All three are read-only in `gen_routing_metadata.py`, and the permission set was regenerated.

**D-L1-4 · `Service_Ticket__c.In_Shop__c` had no field permission anywhere.** A pre-existing gap: no
permission set granted the formula, and nothing read it in user mode before routing.
`RoutingPolicy.assetsInShop` queries it `WITH USER_MODE`, which failed every plan build with the misleading
`Variable does not exist: tmpVar1`. Read access is now in `FleetAdmin` and `FleetforceAdmin`, next to
`Status__c` (the routing permission set leaves fleet-object FLS to the admin sets, D-R2-1). The same scan
found `Service_Ticket__c.Grand_Total__c` without any field permission; routing does not read it, so it was
left alone.

**D-L1-5 · Assert messages must not be null.** Apex throws `Argument 3 cannot be null` whenever the message
of `System.assertEquals` is null, even if the assertion passes. Eight success-path asserts passed
`outcome.get('error')` or `plan.Error__c`, which are null exactly when the test should pass. They now pass
`'error: ' + …` (`RoutingAssistantToolsTest`, `RoutePlanOptimizeJobTest`, `RoutingAssistantIntegrationTest`).
The assistant test classes are unchanged.

**D-L1-6 · `new_org.sh` stops at a failed deploy** (`set -e`), so the permission sets and the App Launcher trim
were run by hand after the deploy succeeded.

**D-L1-7 · The routing seed had never run.** Two fixes in `seed_routing_demo.apex`: Apex names are
case-insensitive, so the constants `DEPOT` and `HUB` clashed with the variables `depot` and `hub` (now
`DEPOT_NAME`, `HUB_NAME`); and the `Rng` inner class (any inner class with a field) made anonymous Apex fail
with an internal server error, so it is now a `between(state, lo, hi)` method with the state in a
one-element list. The numbers are the same, so the city is the same.

**D-L1-8 · A morning sized for openrouteservice.** The seed adds **Beer Sheva South Depot** (4 vans, BSS-03
in the shop, 35 drops) and a plan **Beer Sheva South · morning** set to Openrouteservice, because the
60-drop morning is over the free key's 3 vans and 50 stops. Details in
`docs/Datasets/routing-demo-dataset.md` (Story 1b).

**D-L1-9 · Balanced on openrouteservice, and as the demo objective.** `OrsRoutingProvider` ignored the
objective. It now applies Balanced the way the service does (D-R1-5): `max_tasks` = ⌈tasks / vehicles⌉ + 1
per vehicle, both ends of a shipment counted. Min Distance and Min Vehicles still have no equivalent there
(ORS takes no vehicle costs). Under Min Duration the solver leaves vans idle when fewer finish sooner (the
overnight plan gave one driver all 12 cars), so the South morning and the overnight plan are now seeded
as Balanced.

**D-L1-10 · The board map is Leaflet, not `lightning-map`.** The design only said "map". `lightning-map`
cannot draw lines or label markers, so the board showed loose pins with no order and the stored road path
(`Route__c.Geometry__c`) was never drawn. The new `routeMap` LWC uses Leaflet 1.9.4 (BSD-2, static resource
`Leaflet`) on OpenStreetMap tiles (CSP Trusted Site `OpenStreetMap_Tiles`, images only). It draws one coloured
road line per route from the encoded polyline (dashed straight lines when a route has none), numbered job
stops, B and C for breaks and charge stops, and the depot. `getBoard` now returns each route's geometry. The
board has a driver multi-select, and clicking a route card shows only that route. The OSM tile policy is for
light use only: before a paying customer the tile host must become a setting (e.g. MapTiler or Stadia with a
key). The user chose this on 2026-11-03.

**D-L1-11 · `Geometry__c` off the Route layout, waypoints in route order.** The generator now has
`layout=False` for machine data (the encoded polyline showed as unreadable text on the page) and sorts the
Waypoints related list by Sequence. The field itself and its FLS are unchanged.
